
# ApiForge - Architecture Documentation

## معرفی پروژه (Project Overview)
ApiForge یک پلتفرم تحت وب برای ارسال, مدیریت و تست درخواست های HTTP است که با الهام از ابزارهایی مانند Postman طراحی شده است.
هدف اصلی پروژه, فراهم کردن محیطی یکپارچه برای توسعه دهندگان است تا بتوانند درخواست های API را ایجاد و ارسال کنند, پاسخ های دریافتی را بررسی کنند, درخواست های خود را در قالبت collection مدیریت کند و تست های مختلفی روی API ها انجام دهند.


این پروزه با تمرکز بر موارد زیر توسعه داده میشود : 
- طراحی معماری قابل توسعه و نگهداری
- جداسازی مسئولیت ها و منطق تجاری
- کاهش وابستگی بین بخش های مختلف سیستم
- قابلیت توسعه قابلیت های جدید بدون ایجاد تغییرات گسترده در بخش های دیگر
- رعایت اصول مهندسی نرم افزار و استاندارد های توسعه Backend


## نوع معماری (Architecture Style)
### Modular Monolith
معماری اصلی پروژه بر اساس الگوی Modular Monolith طراحی شده است.

در این معماری تمام ماژول های پروژه در قالب یک برنامه واحد توسعه داده و اجرا میشوند اما از نظر ساختار داخلی مسئولیت ها و منطق تجاری از یکدیگر جدا هستند.

هر ماژول نماینده یک بخش مشخص از سیستم است.

### دلایل انتخاب این معماری
- سادگی توسعه و استقرار : تمام بخش های سیستم در قالب یک برنامه واحد مدیریت و اجرا میشوند.
- جداسازی مسئولیت ها : هر ماژول مسئولیت مشخصی دارد و منطق آن از سایر بخش ها جداست.
- کاهش پیچیدگی عملیاتی : برخلاف Microservice نیازی به مدیریت چندین سرویس مستقل و ارتباطات شبکه ای بین ان ها نیست.
- قابلیت نگهداری : تغییرات داخلی یک ماژول تا حد امکان نباید روی سایر ماژول ها تاثیر بگذارد.
- قابلیت توسعه : در صورت افزایش پیچیدگی سیستم امکان توسعه وجود خواهد داشت.

### ساختار داخلی ماژول ها 
برای طراحی ساختار داخلی هر ماژول از الگوری clean architecture استفاده خواهد شد.

هدف از این انتخاب جداسازی منطق تجاری از جزئیات پیاده سازی و فراهم کردن ساختاری مستقل و قابل نگهداری برای هر ماژول است.



## ماژول های پروژه (Project Modules)
پروژه ApiForge از ماژول های مستقل زیر تشکیل خواهد شد.

هر ماژول مسئولیت مشخصی در سیستم دارد و مالک منطق تجاری مرتبط با حوزه خودش است.

### users
مسئول مدیریت اطلاعات و عملیات مرتبط با کاربران سیستم
قابلیت های اصلی : 
- ایجاد حساب کاربری
- مدیریت اطلاعات کاربران
- ویرایش اطلاعات کاربران

- مدیریت وضعیت حساب کاربری
- دریافت اطلاعات کاربران

### auth
مسئول مدیریت فرآیندهای احرازهویت و مدیریت نشست های کاربران
قابلیت های اصلی : 
- ثبت نام و ورود کاربران در ارتباط با ماژول users
- احراز هویت کاربران
- صدور و اعتبار سنجی JWT
- مدیریت access token و refresh token
- مدیریت نشست های کاربری
- خروج کاربران از سیستم

### workspace
مسئول مدیریت فضای کاری کاربران و سازماندهی منابع مرتبط با آن ها
قابلیت های اصلی :
- ایجاد workspace
- ویرایش و حذف workspace
- مدیریت اعضای workspace
- مدیریت دسترسی کاربران به workspace
- فراهم کردن بستری برای سازماندهی منابع پروژه

### api client
مسئول مدیریت و اجرای درخواست های HTTP
قابلیت های اصلی :
- پشتیبانی از متد های HTTP
- مدیریت URL و Query Parameters
- مدیریت Headers
- مدیریت Path Variables
- پشتیبانی از انواع مختلف Request Body
- مدیریت Authentication درخواست ها
- مدیریت Cookie ها
- ارسال درخواست و دریافت Response

### collections
مسئول سازماندهی و مدیریت درخواست های ذخیره شده
قابلیت های اصلی :
- ایجاد, ویرایش و حذف collection
- ایجاد و مدیریت folder
- ذخیره request ها
- پشتیبانی از ساختار تو در تو
- مرتب سازی درخواست ها
- جابه جایی درخواست ها و Duplicate
- مدیریت تنظیمات و متغییرهای collection
- collection کردن export

### environments
مسئول مدیریت محیط‌های مختلف و متغیرهای مورد استفاده در درخواست‌ها
قابلیت های اصلی :
- ایجاد، ویرایش و حذف Environment
- مدیریت Environment Variables
- مدیریت Global Variables
- مدیریت متغیرهای محلی
- انتخاب Environment فعال
- جایگزینی متغیرها در درخواست‌ها

### history
مسئول نگهداری و مدیریت تاریخچه درخواست‌های ارسال‌شده
قابلیت های اصلی :
- ذخیره تاریخچه درخواست‌ها
- نگهداری اطلاعات Response
- مشاهده درخواست‌های قبلی
- جست‌وجو در تاریخچه
- حذف تاریخچه

### testing
مسئول مدیریت و اجرای تست‌های مرتبط با APIها
قابلیت های اصلی :
- تعریف تست برای درخواست‌ها
- بررسی وضعیت Response
- اعتبارسنجی اطلاعات دریافتی
- اجرای مجموعه‌ای از تست‌ها
- ارائه نتایج اجرای تست‌ها

### documentation
مسئول مدیریت مستندات API ها
قابلیت های اصلی :
- مدیریت مستندات API
- ثبت توضیحات مربوط به Endpointها
- سازمان‌دهی مستندات
- ارائه مستندات قابل مشاهده برای کاربران


## Internal Architecture - Clean Architecture
ساختار داخلی ماژول‌ها بر اساس Clean Architecture طراحی خواهد شد.
هر ماژول در حالت کلی شامل چهار لایه اصلی است:
module/
├── domain/
├── application/
├── infrastructure/
└── presentation/

### لایه domain
لایه Domain هسته منطق تجاری ماژول است.

این لایه مسئول تعریف مفاهیم اصلی و قوانین تجاری مرتبط با ماژول خواهد بود.

### لایه application
لایه Application مسئول پیاده‌سازی جریان‌های اجرایی و عملیات موردنیاز سیستم است.

### لایه infrastructure
لایه Infrastructure مسئول پیاده‌سازی جزئیات فنی و ارتباط با زیرساخت‌های خارجی است.

مانند ارتباط با پایگاه داده، Redis و سایر سرویس‌های موردنیاز

### لایه presentation
لایه Presentation مسئول دریافت ورودی از بیرون سیستم و ارائه خروجی مناسب است.

در ApiForge این لایه عمدتاً شامل Endpointها، Routerها، Schemaها و وابستگی‌های مرتبط با API خواهد بود


## ارتباط ماژول ها (Module Communication)
یکی از اصول مهم در معماری ApiForge، کنترل ارتباط بین ماژول‌ها و جلوگیری از وابستگی مستقیم آن‌ها به جزئیات داخلی یکدیگر است.

### جداسازی ماژول ها (Module isolation)
هر ماژول مالک منطق تجاری و پیاده‌سازی داخلی خودش است.

هیچ ماژولی نباید برای انجام عملیات موردنیاز خود مستقیماً به کلاس‌ها، سرویس‌ها یا جزئیات داخلی ماژول دیگر وابسته شود.

### ارتباطات کنترل شده (Controlled Cpmmunication)
ارتباط بین ماژول‌ها باید از طریق قراردادهای مشخص و کنترل‌شده انجام شود.
برای این منظور از Interfaceها و Contractهای مشخص استفاده خواهد شد.

در نتیجه : 
- وابستگی بین ماژول ها کاهش پیدا میکند.
- تغییرات داخلی یک ماژول تاثیر کمتری روی سایر ماژول ها دارد.
- مسئولیت هر ماژول مشخص باقی می ماند.
- امکان تست مستقل ماژول ها فراهم میشود

### اجزای مشترک (Shared Components)
بخش Shared برای نگهداری اجزایی در نظر گرفته شده است که بین چند ماژول مشترک هستند و به منطق اختصاصی هیچ ماژولی تعلق ندارند.

مسیر اصلی این بخش :
app/shared/

ساختار اولیه :
shared/
├── exceptions/
│   ├── exceptions.py
│   └── exception_handlers.py
│
└── interface/

### exceptions
مسئول نگهداری Exceptionهای عمومی و مشترک پروژه و Handlerهای مرتبط با آن‌ها.

### interface
مسئول نگهداری قراردادها و Interfaceهای مشترکی که در بخش‌های مختلف پروژه مورد استفاده قرار می‌گیرند.

تنها اجزایی باید در Shared قرار بگیرند که واقعاً ماهیت مشترک دارند. منطق اختصاصی هر ماژول باید در همان ماژول باقی بماند.


## Core Components
بخش Core شامل تنظیمات و قابلیت‌های زیرساختی عمومی موردنیاز برنامه است.

مسیر اصلی :
بخش Core شامل تنظیمات و قابلیت‌های زیرساختی عمومی موردنیاز برنامه است.

مسیر اصلی:
app/core/

ساختار اولیه :
core/
├── config.py
└── security/

### configuration
فایل config.py مسئول مدیریت تنظیمات عمومی برنامه خواهد بود.

مانند :
- تنظیمات محیط اجرا
- متغیرهای محیطی
- تنظیمات اتصال به سرویس‌ها
- تنظیمات عمومی برنامه

### security
بخش Security برای نگهداری ابزارها و قابلیت‌های امنیتی عمومی پروژه در نظر گرفته شده است.


### Database
بخش Database مسئول مدیریت زیرساخت ارتباط با پایگاه داده و تنظیمات مرتبط با آن است.

مسیر اصلی :
app/database/

ساختار اولیه :
database/
├── base.py
└── session.py

مسئولیت های کلی :
- مدیریت تنظیمات اتصال به پایگاه داده
- ایجاد و مدیریت Sessionها
- فراهم کردن زیرساخت موردنیاز برای تعامل با PostgreSQL
- فراهم کردن زیرساخت مشترک موردنیاز ماژول‌ها برای کار با پایگاه داده


## Api Structure
برای مدیریت و سازمان‌دهی Endpointهای پروژه از ساختار نسخه‌بندی‌شده API استفاده خواهد شد.

ساختار اولیه :
app/api/
└── v1/
    └── api.py

هدف از این ساختار، مدیریت نسخه‌های مختلف API و فراهم کردن امکان توسعه نسخه‌های جدید بدون ایجاد اختلال در نسخه‌های قبلی است.



### Testing Structure
تست‌های پروژه در مسیر جداگانه‌ای خارج از ساختار اصلی Application نگهداری خواهند شد.

ساختار اولیه :
tests/
└── unit/

هدف از این جداسازی، فراهم کردن ساختاری مستقل برای تست بخش‌های مختلف پروژه و جلوگیری از ترکیب کدهای تست با کدهای اصلی برنامه است.

ابزار اصلی تست پروژه Pytest خواهد بود.
